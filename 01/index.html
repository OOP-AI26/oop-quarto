1. Class Method

Gunakan @classmethod saat method berhubungan dengan class, bukan satu object tertentu.

class Pengguna:
    def __init__(self, nama, username, saldo):
        self.nama = nama
        self.username = username
        self.saldo = saldo

    @classmethod
    def dari_string(cls, data):
        nama, username, saldo = data.split(",")
        return cls(nama, username, int(saldo))

Ingat

  • menerima cls
  • cocok untuk alternative constructor
  • dapat membuat instance melalui cls(...)
  • Ingatkan bahwa setiap method biasa menerima self karena bekerja pada satu instance tertentu.
  • Class method menerima cls, sehingga method bekerja pada level class dan dapat digunakan tanpa memilih instance tertentu sebagai konteks utama.
  • Alternative constructor adalah use case yang paling mudah dipahami: kita punya format input lain lalu mengubahnya menjadi object.
  • Pada contoh dari_string, data dipisahkan dengan split, lalu dibuat object memakai cls(...).
  • Tekankan kenapa memakai cls(...) lebih baik daripada langsung menulis Pengguna(...): subclass dapat mewarisi constructor alternatif tersebut dengan benar.
  • Kaitkan dengan tugas: mahasiswa tidak hanya diminta menulis @classmethod, tetapi menjelaskan mengapa method tersebut memang bersifat class-level.

2. Static Method

Gunakan @staticmethod untuk fungsi yang secara logis milik class, tetapi tidak membutuhkan self maupun cls.

class Pengguna:
    @staticmethod
    def validasi_saldo(saldo):
        return saldo >= 0

Pertanyaan kunci

Butuh data object? → self
Butuh informasi class? → cls
Tidak butuh keduanya? → pertimbangkan staticmethod

  • Bedakan dengan class method: static method tidak menerima self maupun cls.
  • Gunakan contoh validasi saldo untuk menunjukkan bahwa fungsi tersebut tidak perlu membaca atau mengubah object tertentu.
  • Secara konsep, fungsi masih diletakkan di dalam class karena relevan dengan domain Pengguna.
  • Tekankan rule sederhana: perlu state instance → self; perlu informasi class → cls; tidak perlu keduanya → pertimbangkan staticmethod.
  • Jangan menyampaikan bahwa semua helper function harus menjadi static method; penekanannya adalah pada keterkaitan logis dengan class.
  • Di tugas, mahasiswa harus bisa memberikan alasan desain, bukan sekadar memenuhi checklist syntax.

3. Decorator: Ide Dasarnya

Decorator adalah cara untuk membungkus function dan menambahkan perilaku tanpa mengubah isi function utama.

def log(func):
    def wrapper(*args, **kwargs):
        print(f"[LOG] Menjalankan {func.__name__}()")
        result = func(*args, **kwargs)
        print(f"[LOG] {func.__name__}() selesai")
        return result
    return wrapper
@log
def proses():
    print("Memproses transaksi...")

Mental model: proses() → wrapper() → proses asli

  • Mulai dari masalah: kita ingin menambahkan logging pada banyak function tanpa menyalin kode logging ke setiap function.
  • Jelaskan bahwa decorator menerima function sebagai input dan mengembalikan function lain, biasanya berupa wrapper.
  • Pada contoh, @log secara konsep sama dengan membungkus function proses menggunakan log(proses).
  • Tunjukkan alur eksekusi: pemanggilan proses() sebenarnya masuk ke wrapper, wrapper mencetak log, memanggil function asli, lalu mencetak log selesai.
  • Jelaskan fungsi return result: decorator tetap mempertahankan nilai return dari function asli.
  • functools.wraps belum menjadi fokus utama slide ini; detail tersebut bisa muncul ketika membahas custom decorator.

4. Custom Decorator untuk Tugas

Kita membutuhkan decorator yang menjadi guard sebelum transaksi diproses.

from functools import wraps

def butuh_pembayaran(func):
    @wraps(func)
    def wrapper(*args, **kwargs):
        transaksi = args[0]

        if transaksi.pembayaran.status != "VALID":
            print("Pembayaran belum valid.")
            return None

        return func(*args, **kwargs)

    return wrapper

Decorator ini melakukan pengecekan sebelum method utama dijalankan.

  • Di project, decorator tidak hanya logging; kita butuh aturan bisnis yang dapat dipasang ke method tertentu.
  • butuh_pembayaran bertindak sebagai guard: sebelum method utama berjalan, periksa status pembayaran.
  • args[0] pada method instance biasanya adalah object self, sehingga pada contoh transaksi = args[0].
  • Jika status bukan VALID, wrapper menghentikan proses dengan return None; function asli tidak dipanggil.
  • Jika valid, wrapper meneruskan seluruh argument ke function asli menggunakan func(*args, **kwargs).
  • Jelaskan @wraps(func) sebagai praktik baik agar metadata function seperti nama dan docstring tetap terjaga.
  • Hubungkan ini dengan separation of concerns: method proses() fokus memproses transaksi, sedangkan decorator menangani aturan “harus sudah dibayar”.

5. Kenapa *args dan **kwargs?

Wrapper sebaiknya tidak terlalu bergantung pada bentuk parameter function yang dibungkus.

def decorator(func):
    def wrapper(*args, **kwargs):
        return func(*args, **kwargs)
    return wrapper
  • *args → positional arguments
  • **kwargs → keyword arguments

Dengan ini decorator dapat membungkus method dengan parameter yang berbeda.

  • Jelaskan masalah jika wrapper ditulis dengan parameter yang terlalu spesifik: decorator hanya cocok untuk satu bentuk function.
  • *args menampung semua positional argument tanpa perlu mengetahui jumlah dan namanya sejak awal.
  • **kwargs menampung keyword argument dengan nama parameter yang fleksibel.
  • Yang paling penting adalah wrapper dapat meneruskan argument tersebut kembali ke function asli.
  • Pada instance method, self biasanya masuk sebagai salah satu positional argument, sehingga wrapper tidak perlu mendefinisikan self secara eksplisit.
  • Hubungkan dengan chaining dan reusable decorator: semakin generik wrapper, semakin banyak method yang dapat menggunakan decorator yang sama.
  • Mahasiswa harus dapat menjelaskan perbedaan args sebagai tuple dan kwargs sebagai dictionary.

6. Chaining Decorator

Beberapa decorator dapat dipasang pada satu method.

@log
@butuh_pembayaran
def proses(self):
    print("Transaksi diproses")

Secara konseptual:

proses
  ↓
log
  ↓
butuh_pembayaran
  ↓
method asli

Perhatikan

Urutan penulisan decorator memengaruhi urutan wrapper yang membungkus function.

  • Jelaskan bahwa beberapa decorator dapat membungkus function yang sama secara berlapis.
  • Untuk @log di atas @butuh_pembayaran, secara konseptual decorator paling dekat dengan function diterapkan lebih dulu: log(butuh_pembayaran(proses)).
  • Akibatnya pemanggilan masuk ke wrapper log, lalu diteruskan ke wrapper butuh_pembayaran, lalu baru ke method asli.
  • Ini penting karena urutan decorator dapat mengubah perilaku program.
  • Mintalah mahasiswa memperhatikan output saat satu decorator menghentikan proses: decorator di bagian luar tetap bisa menjalankan kode sebelum/ sesudah pemanggilan inner wrapper.
  • Pada tugas lanjutan, mahasiswa akan menambah @cek_nominal untuk melihat lebih jelas efek urutan chaining.

Expected Flow

Skenario A — Valid

[LOG] Menjalankan proses()
[CHECK] Pembayaran valid.
Transaksi berhasil diproses.
[LOG] proses() selesai

Skenario B — “Boskyuh”

[LOG] Menjalankan proses()
[CHECK] Pembayaran tidak valid.
Transaksi tidak dapat diproses.

Yang harus terlihat

Decorator bukan hiasan — ia benar-benar mengontrol flow program.

  • Bandingkan dua skenario dengan input berbeda tetapi struktur program yang sama.
  • Pada skenario valid, decorator logging aktif dan guard pembayaran lolos sehingga method asli benar-benar berjalan.
  • Pada skenario “boskyuh”, logging tetap bisa muncul, tetapi guard menghentikan eksekusi sebelum business logic utama dijalankan.
  • Ini adalah momen penting untuk menunjukkan bahwa decorator memengaruhi control flow, bukan sekadar menghasilkan output tambahan.
  • Saat live demo, gunakan dua object Pembayaran yang hanya berbeda pada field bukti.
  • Minta mahasiswa mengamati perbedaan status akhir transaksi dan kapan pesan dari method asli muncul atau tidak muncul.

Tantangan: 3 Decorator Sekaligus

Tambahkan decorator:

@cek_nominal

Lalu gunakan:

@log
@cek_nominal
@butuh_pembayaran
def proses(self):
    ...

@cek_nominal harus memastikan:

harga barang == nominal pembayaran

Jika tidak sesuai → transaksi ditolak.

  • Tambahkan aturan bisnis kedua: nominal pembayaran harus sesuai dengan harga barang.
  • cek_nominal dapat membaca transaksi dari args[0], lalu membandingkan harga dengan nominal pembayaran.
  • Setelah itu mahasiswa memiliki tiga lapisan concern: logging, nominal validation, dan payment validation.
  • Ini adalah tempat yang baik untuk meminta mahasiswa memprediksi urutan output sebelum menjalankan program.
  • Bahas konsekuensi urutan decorator: apakah logging tetap mencatat proses jika validasi gagal? kapan validasi nominal terjadi? kapan validasi pembayaran terjadi?
  • Pastikan setiap decorator tetap menerima *args dan **kwargs sehingga chain tetap kompatibel.
